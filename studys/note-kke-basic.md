## 쿠버네티스와 카카오클라우드의 쿠버네티스 엔진 서비스의 기본 개념 정리
### MSA(Micro Service Architecture)의 등장과 가상화 기술
1. 소프트웨어 개발의 진화 과정<br>
- 모놀리식 아키텍쳐(MA): 모든 요소(코드)를 하나의 어플리케이션에 구축해서 배포하는 방식. 형태가 단순해서 유지보수가 편리하지만 부분 장애가 전체 서비스의 장애로 확대될 수 있다. 
- 서비스 지향 아키텍쳐(SOA): 서비스를 중심으로 한 방식, 느슨한 결합을 지향
- 마이크로 서비스 아키텍쳐(MSA)(현재): 각 서비스를 독립적으로 개발, 배포, 운영할 수 있는 구조
  -> 서비스가 모두 분산되어 복잡할 수도..

2. 가상화 기술<br>
= 실제 리소스를 추상화하고, 여러 개의 가상환경을 생성하는 기술

- 가상 머신(Virtual Machine, VM) : 하나의 물리적 서버에서 여러 개의 독립적인 가상 서버를 운영할 수 있도록 하는 기술
- 컨테이너 가상화(containerization) : 호스트 os 하나를 공유하고, 도커(Docker)와 같은 컨테이너 엔진이 서비스별 공간인 컨테이너를 만들어줌. os부터 응용 프로그램까지 모든 종속성을 컨테이너로 패키지화 하면 빠른 배포가 가능하다.

### MSA와 컨테이너 가상화의 연관성

1. 독립적 배포 및 확장성

마이크로 서비스는 필요에 따라 개별적으로 확장/변경할 수 있는 환경이 필요하다. 컨테이너 기술은 각 서비스를 격리할 수 있기 때문에 유용.. 또한 이렇게 수많은 컨테이너가 잘 돌아가도록 감시하고, 관리하는게 쿠버네티스이다. = 컨테이너 오케스트레이션

2. 배포 및 유지보수 용이성

마이크로서비스 특성 상 배포와 롤백 등의 버전 관리가 잦은 편인데, 컨테이너 이미지나 가상머신 스냅샷을 사용하면 일관성 있고 빠른 배포가 가능하다.

### 쿠버네티스(Kubernetes) 개요
1. 등장배경 = 컨테이너 관리, 컨테이너 오케스트레이션의 중요성이 대두됨

2. 특징
- 선언적 배포: 개발자는 자신이 원하는 어플리케이션의 상태를 선언적으로 정의한다. 현재 상태를 관찰하고, 원하는 상태로 수렴시키는 과정을 반복
- 자동화된 스케일링: 어플리케이션의 부하에 따라 자동으로 리소스를 확장/축소함
  <img width="1510" height="540" alt="image" src="https://github.com/user-attachments/assets/44a8875e-78d0-4ab0-bc74-ad93524fa9c0" />
  (CA에서 노드 = 워커노드 로 이해하기)<br>
  -> CA는 클러스터 전체적인 물리적 자원이 부족할 때 사용되는 개념이다. 기존 워커 노드에 더 이상 새로운 파드(컨테이너)를 띄울 공간이 없다면, 새로운 워커노드가 자동으로 생성된다. 클러스터가 수용 가능한 워크로드를 최적화!
  
- 자가 치유: 실패한 컨테이너를 재시작하고, 워커 노드가 죽는 경우 응답하지 않는 컨테이너를 종료시켜서 클러스터의 안정성과 가용성을 유지한다.
  
  #### 관련 리소스
 - replica sets: 특정 파드의 복제본을 정의된 수만큼 유지되도록 관리하는 쿠버네티스 리소스
 - liveness probes: 파드 내 어플리케이션이 정상적으로 동작 중인지 확인하고, 문제가 발생하면 해당 컨테이너를 재시작함
 - readiness probes: 어플리케이션이 트래픽을 수용할 준비가 되었는지 확인하고, 준비되지 않은 파드는 서비스로 노출되지 않게 함

### 쿠버네티스 기본 개념
   
#### 파드란?<br>
= 최소 배포 단위, 하나 이상의 컨테이너로 이루어진다. 

<img width="320" height="220" alt="image" src="https://github.com/user-attachments/assets/8d00aa68-e850-493b-993e-43556eac89b1" />

#### 노드란?<br>
= 컨테이너화된 어플리케이션인 파드를 실행하는 서버, 워커 노드와 마스터 노드로 나뉜다. 

<img width="1000" height="350" alt="image" src="https://github.com/user-attachments/assets/aaa9e637-1f84-49db-a1ba-bfa4e9f674dc" />

- 마스터 노드 = 클러스터 운영을 위한 인프라가 모여서 함께 동작하는 노드, 클러스터 내 워커노드에게 작업을 할당한다.

  #### 마스터 노드 구성요소
  1. api server = api 엔드포인트를 제공하여 클러스터 - 사용자 간 상호작용을 담당한다.
  2. etcd = 클러스터의 구성, 상태, 메타데이터 등을 저장하는 분산 키-값 스토어
  3. 스케쥴러 = 새로운 파드를 어떤 워커노드에 할당할지를 결정하는 스케쥴러(파드 생성할 때의 정책에 따라 결정됨)
  4. 컨트롤러 매니저 = 다양한 컨트롤러를 실행해서 클러스터의 상태를 원하는 상태로 유지한다.
  
- 워커 노드 = 컨테이너가 실행되어서 실제로 작업이 수행되는 노드, 마스터 노드의 지시에 따라 컨테이너를 실행하고 관리한다.

  #### 워커 노드 구성요소
  1. kubelet = 마스터 노드로부터 할당된 파드를 워커노드에서 실행하고 관리하는 주체, 노드 상태를 마스터 노드에게 주기적으로 보고함
  2. kube proxy = 서비스의 클러스터 ip와 포트를 실제 파드에 매핑한다.(로드밸런싱 수행)
  3. 컨테이너 런타임 = 컨테이너를 실행하고 관리하는 소프트웨어 = 도커 = 컨테이너 이미지를 다운로드하고, 컨테이너의 실행/종료 담당

#### 클러스터란?<br>
= 여러 노드로 구성된 하나의 컴퓨팅 리소스 집합(kke에서 가장 먼저 생성)

#### !! 파드는 하나 이상의 컨테이너를 포함하는 배포 가능한(최소) 컴퓨팅 단위, (워커) 노드는 하나 이상의 파드가 실행되는 가상머신 서버이다.  컨테이너는 실행되는 어플리케이션 그 자체 !!

### 쿠버네티스 오브젝트<br>
= 어플리케이션의 상태를 나타내는 엔티티로 특정 리소스를 뜻한다. 총 다섯 개가 있다(파드 서비스 볼륨 인그레스 네임스페이스)

1. 파드
   - 독립적인 공간과 ip를 가지고, 동일한 파드에서 실행되는 (서로다른) 컨테이너 간 네트워크와 스토리지는 공유된다.
2. 서비스
   - 파드를 통해 실행되고 있는 어플리케이션을 네트워크에 노출시키는 역할을 담당

#### 서비스가 필요한 이유<br>
-> 파드는 언제든 죽을 수 있는 일시적인 존재이다. 파드가 새로 생성될 때마다 내부 ip주소가 바뀌기 때문에, 다른 파드나 외부 사용자는 파드에 고정된 ip로 접근하는 것이 거의 불가능하다. 따라서 서비스는 여러 개의 파드를 그룹화하고, 이를 대표하는 고정된 ip(= 클러스터 ip)와 dns 이름을 노출한다.

<img width="600" height="615" alt="image" src="https://github.com/user-attachments/assets/17d35faa-404c-4274-8a44-da1da84e25b3" />

(빨간색 = 노드포트, 파란색: 어플리케이션 포트, 각 노드에 붙은 ip = 실제 노드풀(노드) 생성 시 할당된 ip)
(노란색 서비스 = 클러스터 ip, 이 사진은 클러스터 ip를 포함한 노드포트 유형을 설명한다.)

#### 서비스 타입
1. 클러스터 ip = 내부 전용
  - 서비스 타입을 지정하지 않았을 때의 기본값. 클러스터 내에서만 통용된다.

2. nodeport = 외부 허용(노드포트 포함)
   - 클러스터에 속한 모든 워커 노드의 지정된 고정 포트(30000~32767)를 개방하는 방식(빨간색 입구). 로드밸런서가 없어도 외부에서 노드의 클러스터 ip와 포트번호를 통해 접속할 수 있다. 하지만 노드의 ip가 바뀌면 접속 주소도 바꿔야하기 때문에 번거로움.. 또한 노드가 죽으면 접근이 불가하다.
   - 노드포트 생성 시 흐름: 사용자가 직접 노드포트를 통해 워커노드에 접근 - 서비스가 각 파드로 트래픽을 분산
   
3. 로드 밸런서 = csp에서 제공하는 로드밸런서를 사용하는 방식(클러스터 ip, 노드포트 포함)
   - 이 타입을 지정하면 자동으로 로드밸런서 인스턴스가 만들어지고, 로드밸런서에 공인 ip가 할당된다.
   - 로드밸런서 생성 시 흐름: 사용자가 공인 ip를 통해 로드밸런서에 접속(노드포트 유형에 추가된 단계) - 로드밸런서는 받은 트래픽을 각 워커노드에 할당된 포트로 보냄(= 노드포트) - 각 노드의 쿠브프록시가 트래픽을 받고 실제 목적지인 파드로 클러스터 ip와 포트를 통해 전달한다. 

#### 로드밸런서를 사용하는 이유?
= 단일 진입점을 제공한다. Health check로 한 노드가 죽어도 다른 노드로 트래픽을 보내서 고가용성을 유지한다. 

#### 로드밸런싱 사용 두가지 방식

<img width="700" height="600" alt="image" src="https://github.com/user-attachments/assets/e5faf802-d88c-4dfe-be6a-46d0780a2679" />

1. 서비스 로드밸런싱(방금 배운 것)
   - 로드밸런서는 파드 그룹(노드)에 대한 단일 엔드포인트를 제공한다. 
   - 로드밸런서를 통해 내/외부 트래픽을 해당 파드 그룹으로 로드밸런싱 한다. = 두가지 역할

2. 인그레스 컨트롤러를 사용하는 로드밸런싱
   - 인그레스는 웹 트래픽을 클러스터 내 서비스로 라우팅하는 규칙을 정의한다. 컨트롤러를 사용하면 이런 규칙을 처리하고, 단일 ip 주소를 통해 여러 서비스에 접근할 수 있게 함.
   - 컨트롤러를 사용하면 트래픽은 컨트롤러 - 서비스(클러스터 ip) - 파드 로 최종 전달된다. 

5. external name = 클러스터 외부에 있는 서비스에 대한 외부 dns 주소로 노드 매핑을 제공하는 방식
   - 쿠버네티스 내부에서 외부 서비스를 마치 내부 서비스인 것처럼 사용하기 위해 쓴다.
   - ip 주소를 사용하는 것이 아닌, 쿠버네티스 내부 dns 서버에 특정 이름을 등록하고, 사용자가 그 이름을 호출하면 외부 도메인 주소로 연결해줌
